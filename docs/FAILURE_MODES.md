# Linux TUN Failure Modes & Defenses (FAILURE_MODES.md)

This document analyzes why Linux TUN mode implementations historically fail (especially in hostile, censored network environments like Iran) and specifies GhostPath's concrete architectural defenses.

---

## 1. Routing Loops (Self-Capture)

### The Failure Mode
When a VPN sets a default route to its TUN interface (`0.0.0.0/0 dev tun0`), any outbound packet generated by the VPN client's own proxy core to the remote server gets routed back into the TUN interface. This creates an immediate routing loop, locking up the CPU and freezing networking.
Naive solutions attempt to add a static `/32` route to the proxy server IP via the original default gateway:
```text
ip route add <SERVER_IP>/32 via <GATEWAY_IP> dev eth0
```
This fails catastrophically under modern censorship conditions:
1. Censorship-resistant setups utilize CDNs (Cloudflare, Fastly, Cloudfront) or domain fronting where server IPs change rapidly across DNS resolutions.
2. Multi-homed setups or servers with anycast IPs break when the route points to an obsolete IP.

### GhostPath Defense
- **Socket Marking (`SO_MARK`):** GhostPath configures `SO_MARK = 0x4750` on all sockets created by the outbound proxy core.
- **Policy Routing Priority:** GhostPath installs a high-priority Netlink IP rule:
  ```text
  ip rule add fwmark 0x4750/0x4750 table main priority 5180
  ```
  Any packet originating from the proxy core matches this rule first and is routed via `main` (the physical gateway), completely immune to domain IP changes or DNS re-resolutions.

## 2. Default Route Hijack Ordering & Collisions

### The Failure Mode
Overwriting the default route (`ip route del default; ip route add default dev tun0`) destroys existing gateway information. If the VPN crashes or is terminated without cleaning up, the system is left with no working default route and no internet access.
Furthermore, if NetworkManager renews a DHCP lease while the VPN is active, it re-inserts its own default route with a lower metric, silently bypassing the VPN tunnel.

### GhostPath Defense
- **Isolated Routing Table:** GhostPath never touches or deletes the default route in table `main`.
- Instead, GhostPath writes its default route to dedicated table `5180`:
  ```text
  ip route add default dev ghost0 table 5180
  ip rule add not fwmark 0x4750 table 5180 priority 5181
  ```
  Even if NetworkManager renews DHCP and updates table `main`, rule `5181` diverts all non-marked traffic to `ghost0` in table `5180`. Table `main` remains pristine.

## 3. DNS Leaks, Poisoning, and Subsystem Conflicts

### The Failure Mode
On modern Linux distributions, DNS is handled by three competing mechanisms:
1. `systemd-resolved` (listens on `127.0.0.53:53` and manages per-link DNS via D-Bus).
2. `NetworkManager` (which may write directly to `/etc/resolv.conf` or spawn `dnsmasq`).
3. Direct `/etc/resolv.conf` (static or overwritten by DHCP clients).

If a VPN client merely writes `nameserver 1.1.1.1` to `/etc/resolv.conf`, `systemd-resolved` ignores it, and applications querying `127.0.0.53` continue using the ISP's DNS resolver. In Iran, the local ISP resolver poisons DNS records for blocked services with fake IPs (e.g. `10.10.34.34`).

### GhostPath Defense
- **D-Bus Integration with `systemd-resolved`:** GhostPath detects `systemd-resolved` and uses `zbus` to invoke:
  - `SetLinkDNS(ifindex, [10.8.0.1])`
  - `SetLinkDomains(ifindex, [("~.", true)])`
  The `"~."` domain directive sets `ghost0` as the exclusive routing domain for all DNS requests.
- **Internal Encrypted DNS Proxy:** Port 53 queries entering `ghost0` are intercepted by GhostPath's internal DNS service, which converts them to remote DNS-over-HTTPS (DoH) requests tunneled through the proxy.
- **Firewall Leak Blocker:** An nftables rule drops any UDP/TCP port 53/853 traffic exiting physical interfaces.

## 4. IPv6 Leaks

### The Failure Mode
If the physical ISP provides IPv6 connectivity (e.g., dual-stack mobile data or fiber) and the VPN only configures IPv4 on its TUN device, modern browsers will attempt IPv6 connections first (Happy Eyeballs / RFC 8305). These connections bypass the VPN tunnel completely, exposing the user's real IP and triggering censorship filters.

### GhostPath Defense
GhostPath enforces a strict **Dual-Stack or Blackhole** policy:
- If IPv6 is enabled in user settings: GhostPath assigns an IPv6 address (`fd00:5180::2/64`) to `ghost0`, configures an IPv6 default route in table `5180`, and routes IPv6 over the tunnel.
- If IPv6 is disabled in user settings: GhostPath applies an nftables blackhole rule dropping all outgoing IPv6 packets on physical interfaces and rejects IPv6 DNS `AAAA` records, preventing any unencrypted leak.

## 5. MTU / MSS Fragmentation Stalls

### The Failure Mode
Filtered networks and DPI middleboxes in Iran frequently drop fragmented packets or packets with MTU > 1420 (common on 4G LTE and PPPoE connections with encapsulated protocol headers). Standard MTU 1500 causes TCP connections to hang indefinitely during the TLS handshake or large payload transfers.

### GhostPath Defense
- `ghost0` defaults to a conservative MTU of `1420`.
- Automatic TCP MSS clamping via nftables in the forward chain:
  - For IPv4: Clamped to `1380` (`MTU - 40`)
  - For IPv6: Clamped to `1360` (`MTU - 60`)

## 6. rp_filter (Reverse Path Filtering) and Docker Conflicts

### The Failure Mode
- **Reverse Path Filtering (`rp_filter = 1`):** In strict mode (`rp_filter = 1`), the kernel drops incoming packets on `ghost0` if the return route does not match the incoming interface.
- **Docker Bridge Conflicts:** Docker installs iptables `FORWARD` rules with default `DROP` and manipulates `PREROUTING`/`POSTROUTING` chains, often interfering with TUN forwarding and causing packet loss.

### GhostPath Defense
- GhostPath automatically sets `rp_filter = 2` (loose mode) or `0` on `ghost0` and associated interfaces via Netlink/sysctl.
- GhostPath excludes Docker bridges (`docker0`, `br-*`) from tunnel interception unless explicitly requested.
- `ghostpath doctor` detects strict `rp_filter` and Docker conflicts and reports actionable fixes.

## 7. Crash Recovery & Network Deadlocks

### The Failure Mode
If a VPN daemon crashes, receives `SIGKILL`, or panics, the system may be left with orphan `ghost0` interfaces, dangling routing tables, and modified DNS settings, rendering the computer completely offline.

### GhostPath Defense
- **Atomic Undo Journal:** Every route, rule, DNS setting, and firewall modification is recorded to `/var/lib/ghostpath/undo_journal.json` before being applied.
- **Startup Recovery:** When `ghostpathd` launches, it checks for an existing journal. If the previous process crashed, `ghostpathd` reads the journal and executes an idempotent cleanup pass before proceeding.
- **Graceful Signal Handling:** Rust signal handlers intercept `SIGINT`, `SIGTERM`, and `SIGHUP` to execute an orderly RAII teardown.
